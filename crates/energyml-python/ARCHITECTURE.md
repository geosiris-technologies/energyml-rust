# energyml-python - architecture

Related decisions: [ADR 0012](../../docs/adr/0012-no-face-carries-logic.md) (no face carries logic), [ADR 0003](../../docs/adr/0003-identity-full-uri-one-door.md), [ADR 0002](../../docs/adr/0002-storage-trait-follows-etp.md), [ADR 0016](../../docs/adr/0016-one-crate-one-test-binary.md).

## Purpose and position

The Python face: a pyo3 + maturin bridge over `EpcStore`. It ships as the distribution `energyml-rust` and is imported as `energyml.rust` (`energyml.rust.epc`, `.storage`, `.model`, `.resqml`). It is a leaf: nothing depends on it.

## Rules

- **The bridge carries no capability the Rust libraries lack.** A missing capability is written in the crate that owns it (storage, domain, geometry, build) and then bridged. A `session.rs` that *decides* anything is a defect even when the decision is right: the command line and other faces would not have it, and a question would get two answers. The test: if this crate were removed, nothing would be lost but the conversion. What legitimately stays here: converting (dictionaries, numpy, strings), assembling library calls, and naming.
- **What can be wrong is tested natively.** A pyo3 binding runs only after `maturin develop`, so nothing in `bindings.rs` is reachable by `cargo test`. Hence the split: `session.rs` mentions neither pyo3 nor numpy (standard-library types and `String` errors), and `bindings.rs` (behind the `python` feature) only dresses it. `tests/package.rs` exercises the whole bridge without an interpreter.
- **Docstrings are user documentation.** The doc comments in `bindings.rs` are what `help()` shows a Python user; they are written in English with that reader in mind.
- **The scope is read, not promised.** `tests/scope.rs` reads `Cargo.toml` and names both the forbidden and the allowed dependencies, so the next dependency cannot slip in unnoticed. Adding one is a line in that test. Heavy optional components stay out of the wheel (ETP is not part of it).
- **Nothing is installed outside `energyml/rust/`.** Other distributions deposit under `energyml/`. No `energyml/__init__.py` is shipped, so the directory is a PEP 420 namespace package when this bridge is alone and an ordinary subdirectory when another distribution has placed its own; nothing is overwritten. `tests/naming.rs` reads `pyproject.toml` and walks `python/` so a violation fails here instead of breaking someone else's install. The Rust library is named `energyml_rust`, not `energyml`: the CLI binary of that name would collide with it on Windows (a linker database error that names neither target).
- **The abstraction exists before the second store.** `energyml.rust.storage` is the abstract store (drawn after ETP, per ADR 0002), and `Epc` is registered as a subclass; what the abstract class declares is checked at import, so a promised method missing from `Epc` raises an `ImportError` naming it. Rename is deliberately *not* in the abstraction: a network store has no external file to rename, so promising it would promise what the second store cannot keep. The rename quote is returned as a dictionary with `allowed` computed in Rust, so two readers never disagree on whether a refusal is blocking.
- **No class per generated type.** `energyml.rust.model` exposes the Rust reflection (`types()`, `describe()`, `template()`); an object crosses as a dictionary carrying its `$type`, which is what lets `put` know which class to build and a round trip not lose the object. Generating Python classes would be a second copy of the generated crates. A template's `uuid` is left empty on purpose: inventing one would put an object under an identity nobody chose, so `put` refuses and names it.
- **Placement is named, never guessed**: `local`, `projected`, `metres`; an unknown name is refused with the list. A model placed in the wrong system looks exactly like one placed in the right system.
- **Reading a package is the library's reading.** Properties and exports go through the shared scene reader, which brings colours (empty when the package states none: the standard defines no default ramp) and metadata specs (JSON, `{"key": "dotted.path"}`). An export **refuses** if any object cannot be written, naming it, where the command line writes a file per object and skips: a silently truncated single document looks complete. Reprojection is pure Rust, which makes GeoJSON export possible (RFC 7946 is WGS 84 by definition).
- **Arrays pass to numpy by copy.** A shared view would live as long as the package; an array kept after closing it would read freed memory, with the defect surfacing weeks later as wrong numbers or a crash without a stack. A zero-copy method, if ever needed, will say so in its name. Arrays come back flat with their shape alongside, and the file and the path inside it travel together (`ArrayRef`).
- **The door is synchronous.** `EnergymlStorage` is async because an ETP store talks to a server; `EpcStore` has the same operations synchronously, and that is what is bound. Running an executor to wait for a file read would be machinery for nothing.
- **Objects are JSON.** A RESQML object has hundreds of fields; a dictionary is read, edited and rewritten without any line knowing a type.
- **Creating a package costs two decisions the caller must make**: where the `.h5` files go (`set_data_root`, since an EPC names its data files by a bare name relative to a folder) and where the package goes (`save_as`, so one can look before writing).
- **Nothing is on by default.** `default = []`. A workspace member that requires a C library and an interpreter would require them of every other member through feature unification. Three states, each compiled in CI: default (`session` only; an array request refuses and names the feature), `hdf5` (arrays read and written), `python` (the pyo3 binding; it pulls `hdf5`). `pyproject.toml` enables `python`; without it maturin would build an empty module without saying so.
- **The wheel must bundle HDF5**, or it does not import (from Python 3.8 `PATH` is not searched for extension dependencies). The tool differs per platform: Linux uses `maturin build --auditwheel=repair`; Windows uses `delvewheel repair --namespace-pkg energyml`, because `--auditwheel` is a Linux flag that silently does nothing elsewhere. `--namespace-pkg energyml` is required: otherwise delvewheel writes its loader into `energyml/__init__.py`, the one file this distribution must never ship. The CI script checks the produced wheel instead of trusting the flag.
- **The two shipped examples are documentation held by a test.** They build RESQML objects as dictionaries, which no type protects, so `tests/examples.rs` builds the same objects through the same door; modify them together. Their output was also read back by a second reader (the CLI's `check` and `geometry`).
- **A summary is read from the part name; a title requires parsing the part.** `objects()` makes one pass over headers, and an unreadable part keeps its row with an empty title, since removing it would say the package does not contain it.

## Tests

`tests/package.rs` (the bridge without an interpreter), `scope.rs`, `naming.rs`, `examples.rs`, and one file per capability. The array cases need the `hdf5` feature and run in the HDF5 CI script. Run through the workspace (`cargo test --workspace --test package`), not with `cargo test -p`.
